# 已知长度的解码缓冲实验

结论：暂不采用预分配缓冲替代 `Response.arrayBuffer()`。已解压 PLY 的内存流收集可减少约 2ms，但 gzip 路径的差值仅约 1–2ms，样本范围明显重叠；本次没有证明端到端加载或内存峰值收益。

## 方法

基线为 `fc35fbd` 的 `readPlyResponse()`。候选保留相同的输入嗅探、gzip 解压和 PLY 签名检查，仅将最终汇总改为：按场景清单的 `decodedBytes` 分配一个 Uint8Array，逐块 `set()` 写入，结束时检查长度。实验代码位于隔离模块，未接入 `src/viewer.ts` 或生产构建。

使用 pipes 和 office 的完整默认模型，先在计时外准备原始 gzip 和解压后的 PLY，再将相同内存输入以 64 KiB 分块供给。每个场景、每种编码分别预热两个版本一次，然后串行运行 A/B/B/A/A/B/B/A，各版本采样四次，合计 32 个测量样本。每次输出都在计时结束后计算 SHA-256，验证完整字节；输入准备、网络请求、哈希计算均不计入耗时。

计时包含读取器调用、解压（gzip 路径）、校验及最终 ArrayBuffer 返回。每次采样前等一个 rAF；未强制垃圾回收。没有 WebGL 上下文，不测模型初始化、排序、首帧、训练或渲染 FPS，也不把内存中的输入叫作浏览器热缓存。

## 结果

Chromium 153、Apple M5。单位 ms，中位数后为四次样本的最小–最大值。

| 场景 / 输入 | Response 汇总 | 预分配缓冲 |
| --- | ---: | ---: |
| pipes / 已解压 PLY | 11.45（11.10–11.80） | 9.40（8.50–11.20） |
| pipes / gzip | 176.60（175.60–178.10） | 175.30（173.80–177.10） |
| office / 已解压 PLY | 8.95（8.50–9.80） | 7.00（5.70–8.80） |
| office / gzip | 135.60（134.00–137.10） | 133.80（131.10–137.80） |

两场景输出分别为 70,801,551 和 54,618,559 字节，32 次 SHA-256 全部一致，无页面错误。完整样本见[JSON 记录](benchmarks/read-buffer-2026-10-26.json)。场景图片、相机、SH3、高斯数量及默认模型没有修改；未重新进行 GPU 画质实验。

本次主要结论是缓冲汇总只占 gzip 解码路径的一小部分。预分配增加对清单长度、边界和分配失败的处理要求，目前只验证正常完整输入，尚未补齐候选的取消及错误长度回归，因此不作为生产实现保留。

这不是峰值内存对照：两种算法都需要完整输出，且输入已驻留内存。不能由代码少一次潜在汇总就推导峰值下降，也不能用上述差值宣称公网首帧加速。后续优先比较可验证格式的体积、解压与初始化总成本，再决定是否继续缓冲优化。

## 复现

在仓库根目录执行：

```sh
python3 scripts/prepare_read_buffer_experiment.py
npm run dev
```

打开 `/tests/browser/read-buffer.html`，点击 **Run buffer comparison**。脚本从固定历史提交准备两个解码器副本，并建立 `.bin` 硬链接，避免开发服务器替原始 gzip 夹具做 HTTP 自动解压。页面明确验证 gzip 魔数，不进入生产构建。普通 PLY 与 gzip 是两种内存输入实验，不能当作两种真实服务器传输条件。

参考：[Spark 2.4.0 SplatLoader](https://github.com/sparkjsdev/spark/blob/ffe210dc0a45d0515a06c9235878108112827d61/src/SplatLoader.ts)、[SpeedyGS](https://arxiv.org/abs/2607.12656)。后者研究编码复杂度与解码延迟的取舍，本次没有实现其训练或编码器。
