# 新文档首次初始化与 Worker 复用

2026-10-29，基线 `d4b0602`。接续[受控 HTTP 实验](PACED-MODEL.md)，单独检查候选格式较慢的初始化是否仅由首次运行时启动造成。**复用 Worker 后差距仍存在**：pipes / office 的候选初始化中位数为 148.60 / 113.10ms，PLY 为 126.10 / 92.95ms。此次是诊断，没有改变默认加载器、模型或依赖，也没有记录为性能提升。

## 方法与边界

- Spark 2.4.0、Three.js 0.180.0、Chromium 156、Apple M5 / ANGLE Metal / WebGL2。两场景仍为 300,000 / 231,428 点、SH3、关闭 LoD；同一首个留出相机、768 长边、DPR=1、黑色背景。照片与训练/留出划分不变。
- 12 个新文档，每场景/格式各 3 个；每文档串行创建三个新模型，首次一次、同页重复两次，共 36 个样本。组间实际顺序保存在 JSON，不是严格 ABBA；无并行 GPU 实验，所有计时段可见。
- 在导入 Spark / CompareViewer **之前**读取模型并核验 SHA-256；PLY 已用现有读取器完成 gzip 展开，SPZ 保持原始压缩字节，AP16 已解压及验证。每次传入新的缓冲副本，复制位于计时区间外。
- 分别记录动态模块导入、查看器构造、模型初始化、属性恢复与发布、排序稳定等待。模块导入可能包含 Vite 服务与 HTTP 缓存影响，WASM 编译可能与后续阶段重叠；未直接测其独立耗时。没有清理用户缓存或重启浏览器，**不是整页/进程/磁盘缓存冷启动**。
- 初始化从 `new SplatMesh` 前到 `initialized` 完成，包含主线程对象、Worker 调度、解析与结果返回。首帧准备包含着色器/纹理上传、异步排序和帧等待，终点仍是绘制提交，不是 GPU 查询或屏幕呈现。查看器创建两侧上下文，但没有加载 Mesh、照片或其它场景；空 Mesh 场景绘制保留在稳定等待内。
- 测试专用 Worker 包装只记录创建、请求/结果时间和 terminate，不改消息内容。消息耗时由主线程观察，不能等同 Worker CPU 时间。首次后维持同一查看器和解析池，但每个模型都释放并重新创建；没有复用已解析模型。

## 结果

单位 ms，首次每格 3 个样本，同页重复每格 6 个样本，均为中位数。完整最小/最大值和原始样本见[汇总](benchmarks/runtime-init-summary-2026-10-29.json)及[记录](benchmarks/runtime-init-2026-10-29.json)。小样本不推断 P95 或普遍速度提升。

| 场景 / 格式 | 首次初始化 | 同页重复初始化 | 首次稳定等待 | 重复稳定等待 | 首次合计 | 重复合计 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| pipes / PLY | 130.70 | 126.10 | 62.40 | 55.95 | 195.40 | 185.70 |
| pipes / SH8 + AP16 | 153.70 | 148.60 | 62.10 | 53.60 | 219.20 | 205.60 |
| office / PLY | 97.00 | 92.95 | 58.40 | 49.95 | 155.50 | 146.30 |
| office / SH8 + AP16 | 119.40 | 113.10 | 56.60 | 52.50 | 176.80 | 165.95 |

合计为初始化、属性恢复/发布、稳定等待的墙钟时间；各列中位数不可直接相加。候选属性恢复/发布中位数为 0.80–1.55ms，仍在合计内；PLY 小于计时精度的值不代表没有执行。

动态导入中位数为 8.00–9.90ms，范围 7.50–21.30ms；查看器构造中位数为 7.90–8.20ms，范围 7.80–9.70ms。它们另列，未加到表中各模型合计，也不是可部署生产包的脚本冷加载结果。

12 个文档首次各创建两个 Worker：模型解析池一个、排序一个；后两次均没有新 Worker。每文档以“首次初始化减去该文档两次重复初始化的中位数”配对计算，pipes PLY / 候选为 0.60 / 5.70ms，office 为 2.25 / 6.85ms；PLY 配对范围含负值，存在调度波动，不能把差额全归因于 Worker 或 WASM。

**不能只靠预热解释候选的初始化成本。** 同页重复时，候选仍比 PLY 慢 22.50 / 20.15ms。这是当前输入路径的差异：PLY 的 gzip 已在计时外展开，SPZ 的 gzip 仍在解析器内部。与 HTTP 实验中读取量减少带来的总等待收益并不矛盾；不能从本表宣称 PLY 端到端更快，也不直接移植预热。

## 画面与资源

52 次像素对照全部匹配既有 PLY / SH8 + AP16 控制，覆盖每次首个留出画面、两种格式的全部六个留出相机，以及每场景首相机 ±0.08rad。未改相机、分辨率、点数或 SH，未重新训练。候选仍有[既有量化误差](SPZ-ALPHA16.md)；没有重新读取参考照片和计算新的 PSNR/SSIM，也没有把启动顺序变化当作画质收益。偏转检查不等于新的自由漫游实验。

36 个模型各释放一次。每次查看器销毁终止排序 Worker，解析池 Worker 留在该文档的池中；这与 Spark 源码的复用策略一致，不能仅按模型 dispose 次数宣称 Worker 或其 WASM 内存已回收。随后导航/关闭实验页面，没有测真实内存峰值、系统回收时刻或显存占用。

输入预检曾拒绝本地以 `.bin` 命名但实际为 gzip 的 AP16 文件，尚未创建模型。最终夹具改用已有 gzip 读取器并再次校验展开摘要；该失败及早期预检计时不计入正式样本，最早 PLY 样本也用最终夹具重测。原文件未改写。

## 复现与下一步

按 [SH8 + AP16 准备步骤](SPZ-ALPHA16.md#复现与下一步)保留候选文件，运行：

```bash
npm run dev -- --port 5190
```

打开 [runtime-init 夹具](../tests/browser/runtime-init.html)，URL 参数为 `scene=pipes|office&format=ply|spz&sample=0|1|2`，每个组合必须使用新文档。点击运行，保存页面 JSON；`sample=0` 额外核对所有留出与偏转画面。文件存在不等于内容有效，夹具必须先通过摘要检查。

严格类型检查、116 项回归与生产构建通过；生产 JS/CSS 未变。当前没有新的产品入口或 Pages 部署。

下一步优先分解 SPZ 的 gzip 展开、属性转换、跨 Worker 传递与内存峰值。Spark 2.4.0 的 `SpzDecoder` 将裸 NGSP 分支交给 v4 解析，不能直接把浏览器预解压后的 v3 内容当作受支持输入；若试验原生解压，需明确适配器/格式边界、完整校验、取消与峰值内存，再做同画面总耗时对照。暂不为几毫秒首次差额增加常驻预热模型或替换默认 PLY。
